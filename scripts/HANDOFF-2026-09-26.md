## Two findings, one shape: nothing is ever removed

Both are in `FINDING-2026-09-26-no-asset-eviction.md` and
`FINDING-2026-09-26-aggregates-and-indicators.md`.

**An asset, once seen on the wire, is permanent.** `AssetLogistics` is a Restate
Virtual Object whose `on_timer` re-emits with `force_emit=True` and reschedules
**unconditionally**, so one PDU creates a self-sustaining emitter. I had
`STALE_INPUT_SECONDS=300` backwards and corrected it in writing: it is a
*severity rule* (`rules.py:834`) that adds a DEGRADED `stale_inputs` factor and
keeps emitting — **not** an eviction policy. And there are no deletion semantics
anywhere: zero matches for tombstones, null-value guards or `DELETE FROM` across
the projector templates and dynamic mappings. **At work the upgrade wipe that
cleared this in the lab is off by default**, which is the single most important
line in the difference list.

**A withdrawn asset still inflates the rollups.** The regional aggregator's Faust
table is keyed by `asset_id`, `_emit_rollups` iterates every key it has ever
seen, and nothing in that file evicts. The projector downstream is *stateless*
and only upserts. Measured: `region_fleet_summary` reads **4 partials / 15
assets** where the aggregator's own docstring and §E both record **3 / 14**, it
is live rather than stale (`observed_at` advances every 30s), and it **survived
two cold restarts of the aggregator pod**. The completeness gate passes it
**correctly** — `AGGREGATE_TABLES` inverts the test because a nation on a rollup
would open ADR-0043 §4's first branch — so no gate can see a stale aggregate
partition, and none claims to.

Also worth knowing before the camera is on: **`hq_link_severed` stays `false`
under a `sever-tier.sh` cut**, a whole-table "HQ last updated" tile is **blind to
a single-edge cut** (measured: HQ total read 0s while HQ's edge-01 rows sat 305s
stale), and **staleness gets worse for ~50s after a heal** because the edge
buffer replays oldest-first and `max(last_sample_at)` can regress.

## What the escalation actually taught

The mechanism was reviewed first and *then* run in four escalating stages —
baseline, dry-run, first real run, second real run. **Each stage found a defect
the previous one structurally could not.** That progression is the finding: the
six reviewed judgment calls were all reachable by reading a `--help`; none of the
four found by running were.

* **`--dry-run` cannot discover an interactive CLI.** It prints the command
  instead of executing it, so "this mutating CLI prompts" is only ever found by
  the first real run — the run that is already mid-mutation when it fails. That is
  exactly how run 1 ended. Every mutating CLI in the script now assumes it prompts
  until its own help text says otherwise.
* **An unfalsifiable check is worse than an absent one.** The aggregator verify
  grepped `"asset_count": N` out of a topic that is **protobuf**. It ran, polled
  its full 90-second window, and printed a confident verdict from a grep that
  could never match. An absent check is visibly absent; this one looked like
  diligence. It now reads the projector's decoded column and asserts freshness
  against the **database** clock, not the workstation's — a workstation a few
  seconds ahead makes every row look stale and a correct reset report UNMEASURED.
* **`set -euo pipefail` plus a grep that legitimately matches nothing kills the
  script from inside a command substitution.** The instance found sat in the
  aggregator verify, i.e. it would have fired *after all 210 mutations* — reset
  cluster, no verdict, no summary, exit 1, indistinguishable from a failed reset.
  Three more were latent; all now guarded at the source, so every caller is fixed
  at once rather than call site by call site.
* **Round-trip assertions have to be asymmetric.** Restate object key counts come
  back *exactly* after recovery (14 / 8 / 6 / 14 both times); state row counts come
  back *approximately* (84 / 57 / 42 / 98 against a baseline of 84 / 59 / 43 / 98),
  because entries per key are ragged — 6.00 / 7.38 / 7.17 / 7.00. Assert keys
  exactly and rows in a band, or the check fails on a correct reset.
* **The trim assertion is `log_start == high_watermark`, not `hw == 0`.**
  `trim-prefix` moves the log start offset; it does not rewind the high watermark.

### Call 10 is resolved: capture, delete, recreate, assert

The decision that was left for the operator is taken, and it is a MIXED strategy
rather than a choice between the four options offered:

* policy contains `delete` -> trim, exactly as before, argv unchanged;
* policy is pure `compact` -> delete and recreate, from a config **captured off
  the live broker moments before the delete**.

That is what answers the old header's objection. It refused delete-recreate
because a recreate would need the script to restate the chart's topic matrix, a
second copy that drifts. Capturing from the broker means there is no second copy
at all, and the post-recreate assertion is what turns that from a hope into a
check.

Two facts were settled by measurement, not assumption:

* the split rule, proven on throwaway topics — `compact` is refused
  `POLICY_VIOLATION`, `compact,delete` succeeds. 53 topics land on the recreate
  side: 13 each on hq/edge-01/edge-02/edge-03, 1 on region-east, which is
  consistent with the region-east policy split recorded above.
* `auto_create_topics_enabled=true` on every broker. A deleted topic is a loaded
  gun: anything that touches it makes the broker recreate it at 1 partition and
  delete policy. That is why consumers are scaled to zero across the recreate and
  why the work is per topic rather than bulk — the missing-topic window is kept
  as small as the design allows.

`--red-check-topic-config` perturbs `cleanup.policy` on one recreated topic,
requires the assertion to NOTICE, then restores and requires it to pass again.
Call 8 is the reason that flag exists rather than being optional.

### A half-state path that this change would have opened, closed

Worth recording because it is a property of the script's shape, not of this
feature. Every phase is called bare at the bottom of the file, so under
`set -euo pipefail` a `return 1` from phase 4 aborts before phase 8 restores the
producers phase 2 scaled to zero. Phase 4's new failure path made that reachable
by design rather than only by accident.

A per-phase trap was the wrong fix and was tried first: it rescued the consumers,
left the producers down, and its own `trap - EXIT` would have disarmed any
script-wide trap for phases 5 through 8 — **two traps on EXIT are one trap, and
the second silently wins.** There is now one EXIT trap, armed at the first
scale-down, restoring everything with a recorded original count, guarding each
scale individually and printing the by-hand command for whatever it cannot fix.
It stays silent on a clean run and on a legitimately non-zero phase 9, which is
what a `--skip-*` red-check SUCCEEDING looks like.

Exercised against a standalone harness for all three cases (clean / red-check /
abort mid-phase). **The script itself has still not been run end to end.**
